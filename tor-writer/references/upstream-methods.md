# Upstream analysis methods

Used at Stage 2. The choice depends on what triggered the document.

| Trigger | Tool |
|---------|------|
| An observed problem | **MARP / FRAP** |
| An objective or an opportunity | **OKR** |
| An imposed instruction, no analysis possible | **PESTEL** and/or **SWOT** alone |
| A situation to explore before deciding | **QQOQCCP** |

---

## 1. Problem analysis and resolution method (MARP)

Five phases: identification → findings → recommendations → action plan → follow-up.

### 1.1 Identification

Trigger questions: what is not working as it should? What is generating uncontrolled spending? What
exposes the organisation to a risk it cannot bear? Inverting these questions surfaces opportunities.
A problem anticipated before it occurs is a **risk**.

### 1.2 Findings

Break the problem into five components:

| Component | Writing requirement |
|-----------|---------------------|
| **Title** | Exhaustive and precise; spatial, temporal, qualitative and quantitative information. **No intensity adjectives**: "a 30 to 35% drop in sales", not "a sharp drop". |
| **Description** | How the problem manifests in the activity: facts, actors, stakes, resources involved. |
| **Reference framework** | The requirement being breached: source text (law, standard, decision, good practice), location within the text, quotation if short or paraphrase otherwise. |
| **Causes** | What generates the problem (see 1.3). |
| **Consequences** | The effects of the problem on operations (see 1.4). |

### 1.3 Causes — 5M then 5 Whys

Build a cause-and-effect (Ishikawa) diagram. Classic branches (the French "5M"): **manpower,
method, machine, environment, materials**. Do not stop there: add
branches to fit the context — management, financial means, maintenance, price, process, human
capital, performance, suppliers, skills.

| Branch | Causes identified |
|--------|-------------------|
| Manpower | |
| Method | |
| Machine / equipment | |
| Environment | |
| Materials | |

Then apply the **5 Whys** to each significant cause until the root cause:

| Question | Answer |
|----------|--------|
| Why …? | Because … |
| Why …? | Because … |

**Stopping point**: as soon as a cause lies beyond the organisation's power to act. Stay within what
is actionable — sometimes three whys suffice, sometimes seven are needed.
**Validation filter**: "does this cause directly or indirectly produce the identified problem?" If
not, discard it.

### 1.4 Consequences

Change the question: no longer "why?" but "what damage does or could this problem do to the
activity?". Organise using the same branches as the causes.

### 1.5 Recommendations — two families

| Family | Target | Logic |
|--------|--------|-------|
| **Preventive** | The **causes** | Prevent recurrence |
| **Corrective** | The **consequences** | Neutralise effects already produced |

*Guiding image*: fixing the burst pipe (preventive) is not enough — water has spilled and must be
mopped up (curative). Both families are mandatory.

Write each recommendation as an infinitive verb, one verifiable action.

### 1.6 FRAP — the problem analysis and resolution sheet

Reporting format, one sheet per problem:

| Item | Content |
|------|---------|
| Reference | Sequence number |
| Title | Title of the problem |
| Statement of facts | How the problem manifests |
| Reference framework | The good practice or requirement breached |
| Causes | Causes retained after filtering |
| Consequences | Consequences retained after filtering |
| Recommendations | Preventive and corrective, kept distinct |
| Deadline | Time to implement all recommendations |
| Owner(s) | Who must act and own the solution |

### 1.7 Prioritising the recommendations

Before moving to the TDR, prioritise:

| Action | Impact (1–3) | Effort (1–3) | Priority (impact ÷ effort) |
|--------|--------------|--------------|----------------------------|

Sort by descending priority. High-priority actions go into the immediate TDR; the rest are scheduled
later.

**Pivot point toward the TDR**: a list of recommendations binds no one and produces no change. Only a
TDR — by defining requirements, methods, resources, actors, risks and budget — moves a recommendation
from dormant to active. One diagnosis can give rise to **several staged TDRs**, which avoids budget
blow-ups and lets priorities be handled first.

## 2. OKR — objectives and key results

Use when the document arises from an ambition rather than a problem.

### 2.1 Structure

- **Objective**: a clear vision of the goal. Simple, measurable, attainable, realistic, time-bound.
- **Key results**: quantified indicators measuring progress toward the objective.
- **Initiatives**: the actions and projects that produce the key results. Initiatives are what become
  TDRs.

### 2.2 Three phases

1. **Set the objectives.** E.g. increase sales by 20%.
2. **Set the key results.** Identify every action that moves the objective, then for each the
   quantitative measure and its target value.
   *Technique*: treat the objective as a problem — "what could prevent us from reaching it?" — and
   explore the branches of an extended cause-and-effect diagram (management, finance, maintenance,
   product, price, promotion, process, human capital, physical evidence, performance, environment,
   suppliers, skills).
3. **Define the initiatives.** For each key result: which method, which resources, which schedule?
   This lands exactly back on MPR.

### 2.3 Ambition level

Target: **reach at least 70%** of key results. Reaching 100% means the objectives were too easy —
raise them in the next cycle.

## 4. SWOT — stakes grid

Each quadrant is analysed through the PESTEL lens.

| Strengths | Weaknesses |
|-----------|------------|
| Assets and resources that let the organisation stand out against the problem the document addresses | Circumstances that hamper the organisation and sustain the problem |
| **Opportunities** | **Threats** |
| Favourable openings that can be exploited in solving the problem | Risks and challenges tied to the problem that could damage performance if nothing is done |

---

## 5. QQOQCCP — the seven questions

What · Who · Where · When · How · How much · Why (French: *quoi, qui, où, quand, comment,
combien, pourquoi*). A rapid collection grid to describe an initial situation, isolate elementary problems and surface
causes and possible solutions. Particularly effective in a group session.

---

## 6. Brainstorming

Recommended for identifying causes, risks and key results. A group of 2 to 3 people who know the
process well. Two strictly separate phases: **generation** without judgement, then **evaluation** of
relevance and feasibility. Retain only hypotheses that carry significant change.

When the skill operates without a human group, simulate that split: first produce a broad list, then
filter explicitly against the criterion of connection to the context.
