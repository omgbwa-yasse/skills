# Tracking method

## Building a dashboard

Useful columns, in order:

| Column | Content |
|---|---|
| Activity / milestone | Title, taken verbatim from the initial plan — do not reword |
| Owner | A function or a person, never a whole team |
| Planned date (initial) | Fixed from the first version, never rewritten |
| Planned date (revised) | Updated if rescheduled, with the initial date kept alongside |
| Actual / estimated date | What actually happened, or the best current estimate |
| Status | Done / in progress / upcoming / blocked — four states, no more, to stay readable |
| Variance | Calculated, not judged: number of days or weeks |
| Comment | One line: the cause if there's a variance, nothing if on track |

**Colour coding must follow a rule, not an impression.** Define the threshold before colouring: for
example red if the variance exceeds 10% of the activity's planned duration or threatens a contractual
milestone, amber below that but non-zero, green if on track. Colour coding left to the judgement of
whoever fills in the table drifts toward optimism update after update.

**One line = one activity or milestone, never a grouped batch** whose status aggregates different
realities ("Lot 3: in progress" when three of five activities are done and two are blocked hides the
useful information).

## Handling a missed milestone or a blocker

Mandatory order — never propose a fix before completing the first two steps:

1. **Diagnose the cause.** Execution delay (the work takes longer), an unmet external dependency (a
   third party didn't deliver), a missing resource, or scope creep (the work changed in nature). The
   four causes call for different treatments; conflating them produces a catch-up plan that doesn't
   address the real cause.
2. **Measure the downstream impact.** Which later milestones are threatened, which external
   commitment (contractual delivery, regulatory deadline, a date announced to a funder) is affected.
   Quantify the slip in days, not in impression ("it'll probably slip a bit").
3. **Propose treatment options**, with their cost: catch up (extra resources, at what cost),
   reschedule (new date, what downstream impact is accepted), cut scope (exactly what, with whose
   agreement), or accept the delay as-is if the impact is negligible.
4. **Name who decides and by when.** A blocker with no identified decision-maker stays a blocker
   indefinitely.

## Decision log

A chronological register, one line per entry, never rewritten retroactively:

| Date | Decision or event | Reason | Decision-maker | Impact on schedule/budget |
|---|---|---|---|---|

Purpose: reconstruct after the fact why the project deviated from the initial plan — essential for an
end-of-project report or a review with a donor asking for accountability on variances. Log decisions
at the moment they're made, not reconstructed from memory when the report is due.
